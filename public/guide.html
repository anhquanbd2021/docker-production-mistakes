Fix guide

10 checks, mapped to fixes

Every check in the scanner is one line of the article's closing checklist. This page maps each verdict to the control that clears it.

Static analysis, honest limits. The scanner reads text, not builds. It catches patterns, not intentions — treat warn and info as prompts to verify, and always fix fail.

What this demo proves

The vulnerable example passes every local smoke test — it builds, starts, answers — while carrying eight fails and two warnings. The hardened example clears all ten checks with a .dockerignore, pinned alpine base, multi-stage build, non-root user, healthcheck, and limits set at deploy time.

Baked into the image

Checks 1–6

Check 01

No .dockerignore

The build context is sent wholesale to the daemon; COPY . . sweeps whatever sits there.

Fix
A five-line .dockerignore excludes .git, .env*, node_modules and CI credentials.
Check 02

Ignoring layer caching

COPY . . before npm install forces dependency installs to rerun on every code edit.

Fix
Manifests first, install, then source — cheap-to-invalidate layers last.
Check 03

Bloated images

Full-OS bases ship shells and compilers nobody calls — bigger deploys, more CVEs, a toolkit for intruders.

Fix
-slim, alpine, or distroless bases.
Check 04

Skipping multi-stage builds

Build tools installed in a single stage ship forever.

Fix
A builder stage compiles; the final stage copies artifacts via --from=.
Check 05

Secrets in image layers

RUN rm .env adds a layer that masks — the secret stays recoverable from the adding layer.

Fix
BuildKit secret mounts, runtime env/mounts, a secrets manager — then rotate anything that touched a layer.
Check 06

latest in production

A moving tag means untraceable versions and surprise upgrades.

Fix
Pin versions or digests; tag your images with a git SHA.

Only visible at runtime

Checks 7–10

Check 07

Running as root

One app bug becomes a root shell; one escape becomes root on the host.

Fix
USER in the final stage, or --user/runAsNonRoot at runtime.
Check 08

One container, many processes

Side processes are invisible to Docker — they die silently and get killed mid-write.

Fix
One concern per container; sidecars for true neighbors.
Check 09

No health checks

A deadlocked app looks "running" — traffic keeps flowing to a zombie.

Fix
HEALTHCHECK or orchestrator probes that verify real dependencies.
Check 10

No resource limits

One leak can consume the host; the OOM killer may not pick the leaker.

Fix
--memory/--cpus or compose mem_limit/cpus per container.

Architecture

How the demo is built

LayerBehaviorEvidence
Rule engineParses the Dockerfile and scores all 10 checks. Pure ES module shared by browser, CLI, and tests.public/rules.mjs
Layer simulatorReplays COPY/RUN rm into a layer stack; shows merged view vs. per-layer recovery.public/layers.mjs
Context simulatorA .dockerignore matcher (globs, **, ! negation, directory prefixes) that splits the repo into swept vs. excluded.public/context.mjs
ServerZero-dependency static host plus /health and /version. No build step, no Docker required.app/server.js

Run locally

Inspect the evidence

npm test        # rules + layer sim + context matcher + server
npm run scan    # side-by-side report on examples/
npm run check   # both
npm start       # serve the lab on :3000

The scanner never builds anything — paste your own Dockerfile in the lab and watch the verdict change.

Limits

What this demo does not claim

  • Static rules catch patterns, not intentions — a clean scan is not a secure image.
  • Check 1 (.dockerignore) and check 10 (resource limits) live outside the Dockerfile; the lab asks for that evidence explicitly.
  • The .dockerignore matcher covers the common syntax, not every edge of moby/patternmatcher.
  • The layer simulator models file add/remove — not registry compression, squashing, or BuildKit internals.
